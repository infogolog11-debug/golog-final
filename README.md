# Golog (جولوج) — التطبيق الكامل

بُني حسب `golog-spec.md` (والتحديث الخاص باستراتيجية الإطلاق التجريبي): قاعدة
`bashar_Golog-Ride-Share` + منطق OTP من `golog_Golog-Trip` + منطق الرحلات
النسائية والعائلية من `golog_Golog-Trip-Master`، مع **إزالة كاملة لكل
اعتمادية Replit**.

## تحديثات الأمان والتصميم (أُضيفت بعد المراجعة الفنية)

### إصلاحات أمنية حرجة
- **ثغرة تخمين OTP**: كان تأكيد الحجز/تسليم الطرد يقبل عدد لا نهائي من المحاولات (10000 احتمال لرمز من 4 أرقام). أُضيف حد 5 محاولات فقط لكل حجز/شحنة (`otpAttempts` في قاعدة البيانات)، مع رسالة توضح عدد المحاولات المتبقية.
- **3 ثغرات صلاحيات (Authorization)**: كان بإمكان أي مستخدم مسجَّل دخوله رفض حجز أي شخص آخر، أو قبول/رفض أي طلب شحن طرد (بدون التحقق أنه سائق الرحلة أصلاً)، أو تقييم حجز ليس طرفاً فيه. جميعها تتحقق الآن من الصلاحية الفعلية قبل التنفيذ.
- **CORS كان يسمح لأي أصل** (`origin: true` مع `credentials: true`) — هذا تكوين يفتح الباب أمام هجمات CSRF لأي تطبيق ويب خارجي بانتحال طلبات مستخدم مسجَّل دخوله. أُصلح ليتحقق من `WEB_ORIGIN` المحدَّد صراحة.
- **helmet + حدود معدّل الطلبات** (`express-rate-limit`) على كامل الـ API، وحد أشد خصوصاً على مسارات الدخول.
- **`trust proxy`** مفعَّل الآن (ضروري لعمل الكوكي الآمن بشكل صحيح خلف أي بروكسي عكسي كـ Railway/Render)، وإعداد `sameSite` قابل للتهيئة عبر `COOKIE_SAME_SITE` إن استُضيفت الواجهة والباك-إند على نطاقين مختلفين تماماً.

### الهوية البصرية
صُمم نظام بصري كامل مبني على فكرة المنتج نفسه — رحلة بين نقطتين:
- **الألوان**: كهرماني "الطريق" (لون أساسي دافئ) + أخضر صنوبري "المعبر" (ثانوي، لحالة المعبر المفتوح وشارة التوثيق) + خلفية رملية دافئة بدل الأزرق العام الافتراضي.
- **الخطوط**: Reem Kufi (خط Kufi هندسي يستحضر لافتات الطرق) للعناوين، IBM Plex Sans Arabic لنصوص الواجهة، IBM Plex Mono للأرقام (رموز OTP، الأسعار).
- **عنصر التوقيع البصري**: مكوّن `RouteLine` (`components/route-line.tsx`) — نقطة، خط متقطع، نقطة — يحل محل السهم النصي بين "من" و"إلى" في أهم بطاقات الرحلات (الراكب، الحجوزات، السائق)، مع حركة انزياح خفيفة تحترم `prefers-reduced-motion`.

### أدوات تشغيل إضافية
- **سكربت تعبئة أولي** (`packages/db/src/seed.ts`, تشغيل بـ `npm run seed`): يملأ جدول المدن والمعابر بأسماء حقيقية (حلب، إدلب، غازي عنتاب، باب الهوى...) بدل أن يبدأ فارغاً.
- **ترقية أدمن تلقائية**: ضع بريدك في `ADMIN_EMAILS` وسيُرقّى حسابك تلقائياً عند تسجيل الدخول، بدون أي تعديل SQL يدوي.

## تحسينات تجربة المستخدم (بعد مراجعة تركّز على أول استخدام فعلي)

- **صفحة الهبوط أُعيدت كتابتها بالكامل**: النسخة الموروثة كانت تذكر تسجيلاً بالبريد الإلكتروني (لا نستخدمه)، وتدّعي أرقام استخدام كاذبة لمنتج لم يُطلق بعد ("آلاف المسافرين يومياً"). استُبدلت بمحتوى صادق يشرح الميزات الفعلية (رحلات نسائية، شحن طرود، رمز اللقاء) ويجيب على أسئلة الزائر الجديد المتشكك.
- **"رمز اللقاء" بدل OTP التقني**: أُعيدت تسميته في كل الواجهة مع شرح واضح لسبب وجوده، وأُضيف زر لمشاركة تفاصيل الرحلة مع شخص موثوق عبر واتساب (عادة أمان يعرفها الجمهور فعلاً).
- **معالجة مشكلة "البداية من الصفر"**: الشاشات الفارغة (لا رحلات مطابقة / لم تنشر رحلة بعد) أصبحت دعوة فعلية للعمل بدل نهاية مسدودة — تقترح نشر طلب مطابق، وتعرض للسائق عدد الركاب الفعلي الذين ينتظرون رحلات (مسار `/trips?kind=request` جديد في الباك-إند).
- **تقليل احتكاك نموذج نشر الرحلة**: بيانات السيارة تُملأ تلقائياً من الملف الشخصي بعد أول رحلة، وتُحفظ فيه تلقائياً — لا تكرار يدوي.
- **مؤشر ثقة جديد**: "عدد الرحلات المكتملة" يظهر بجانب تقييم كل سائق في نتائج البحث (استعلام SQL مُجمّع من جدول الحجوزات الفعلي).
- **تذكير تيليجرام أبكر**: شريط خفيف قابل للإغلاق في أعلى صفحتي الراكب والسائق، بدل انتظار المستخدم حتى يفتح صفحة الحساب بنفسه.

## اكتشافات إضافية أثناء إعداد خطة النشر (بتشغيل فعلي، لا فحص أنواع فقط)

عند اختبار تشغيل السيرفر فعلياً (وليس فقط `tsc`/`vite build`) لأول مرة، ظهرت مشكلتان حقيقيتان كانتا ستمنعان أي نشر ناجح:

- **`npm run start` كان سيفشل فوراً في الإنتاج** (`ERR_MODULE_NOT_FOUND`): إعداد التجميع كان يُنتج استيرادات ESM بدون امتداد `.js`، وNode يرفضها. الحل: تشغيل الكود مباشرة عبر `tsx` (كما في التطوير) بدل تجميعه إلى JS أولاً — تم تطبيقه، ومُختبر فعلياً الآن (`npm run start` يعمل ويُصدر "Golog API server listening").
- **جلسات المستخدمين كانت في الذاكرة (MemoryStore)** — غير آمنة للإنتاج (تسرّب ذاكرة، ولا تعمل إن شُغِّلت أكثر من نسخة واحدة من السيرفر). استُبدلت بمخزن جلسات فعلي في قاعدة بيانات Postgres عبر `connect-pg-simple` (ينشئ جدول `user_sessions` تلقائياً).

كلا الإصلاحين مُختبران بتشغيل فعلي (`npm run start` مع متغيرات بيئة تجريبية) وليس فقط بفحص الأنواع.

## إعادة تصميم لسهولة الاستخدام (لجمهور يستخدم الموبايل حصراً، وعلى عجلة)

بعد مراجعة الديمو، تبيّن أن التصميم كان أقرب لذهنية "تطبيق ويب نظيف" من ذهنية "سائق يقود بيد ويحمل الهاتف بالأخرى، أو مسافر واقف عند الحدود بإشارة ضعيفة". أُعيد بناء عناصر التفاعل الأساسية بالكامل:

- **شريط تنقّل سفلي بنمط واتساب** (`bottom-nav.tsx`) — 5 أيقونات كبيرة بدل قائمة رأس مزدحمة، يعمل بيد واحدة أثناء المشي أو الوقوف؛ الرأس نفسه أصبح فقط: العلامة التجارية + تبديل الدور.
- **اختيار المدينة بالأزرار** (`city-picker.tsx`) بدل القوائم المنسدلة — ضغطة واحدة مباشرة، لا حاجة لفتح/تمرير/قراءة قائمة.
- **اختيار وقت مبسّط** (`quick-datetime-picker.tsx`) — اليوم/غداً/بعد غد × صباحاً/ظهراً/عصراً/مساءً، مطابق لكيف يفكّر الناس فعلياً بمواعيد السفر؛ مع خيار "وقت دقيق" مطوي لمن يحتاجه.
- **عدّاد مقاعد بأزرار +/-** (`seat-stepper.tsx`) بدل حقل رقمي يحتاج كتابة.
- **مسارات جاهزة بضغطة واحدة** (حلب↔غازي عنتاب وغيرها) في أعلى شاشة البحث.
- **نموذج نشر الرحلة للسائق** أُعيد بناؤه بالكامل: الحقول الأساسية فقط ظاهرة، والثانوية (السعر، المعبر، تفاصيل السيارة) مطوية خلف "تفاصيل إضافية (اختياري)".
- **رقم هاتف السائق أصبح زر اتصال ضخم** بدل رابط نصي صغير، ولوحة أرقام تلقائية عند إدخال رمز اللقاء في كل مكان.
- تسجيل الخروج ولوحة الإدارة انتقلا لصفحة الحساب كأزرار كبيرة (٥٦px) بدل أيقونات صغيرة في الرأس.

## ست إضافات أخيرة لسهولة الاستخدام (مبنية على سياق فعلي: طرقات حدودية، إشارة ضعيفة، تكلفة بيانات)

- **رمز اللقاء يبقى متاحاً بلا إنترنت**: يُحفظ محلياً في المتصفح (`lib/offline-cache.ts`) فور وصوله من السيرفر — أهم لحظة يحتاجه فيها الراكب هي عادة أضعف لحظة اتصال (نقطة عبور حدودية)، فصفحة الحجوزات تعرضه من التخزين المحلي مع تنبيه واضح "لا يوجد اتصال" إن تعذّر الاتصال بالسيرفر.
- **تقليل استهلاك البيانات**: خُفِّض تكرار استعلامات الرسائل والإشعارات في الخلفية (15-20 ثانية → 45 ثانية) لجمهور بباقات إنترنت محدودة، مع إبقاء المحادثة النشطة نسبياً سريعة.
- **مشاركة موقع GPS فعلي عبر واتساب** بدل نص فقط — يحاول الحصول على الموقع الحالي ويُرفقه كرابط خرائط جوجل مع الرسالة، ويتابع بالنص وحده تلقائياً إن رُفض الإذن.
- **شريط الرحلة القادمة** (`active-trip-banner.tsx`) — يذكّر الراكب برحلته المؤكَّدة القادمة أينما تنقّل في التطبيق، بدل الاضطرار للعودة يدوياً لتبويب "حجوزاتي".
- **رسائل صوتية بالضغط المطوّل** في المحادثة (نمط واتساب تماماً) — لأن جزءاً من الجمهور قد لا يرتاح للكتابة؛ التسجيل يُرفع لـ Supabase Storage ويُشغَّل عبر رابط مؤقّت موقَّع.
- **تكبير حجم الخط** من صفحة الحساب (`lib/font-scale.ts`) — ثلاثة مستويات محفوظة محلياً، مفيد لجمهور قد يضم أعماراً أكبر سناً.

## خمس إضافات أخيرة (السادسة — دعم اللغة التركية — أُجِّلت عمداً لقرار لاحق)

- **انتهاء صلاحية الرحلات القديمة تلقائياً**: أي رحلة تجاوز موعدها بأكثر من 12 ساعة تُعلَّم "منتهية" تلقائياً عند القراءة (`lib/expireTrips.ts`، بأسلوب lazy expiration بلا حاجة لمهمة مجدولة) — بدل أن تبقى رحلة انتهت ظاهرة في نتائج البحث فتُحبط راكباً يحجزها.
- **زر "وصلت" للسائق**: يرسل إشعاراً فورياً للراكب فور اقتراب السائق من نقطة اللقاء، قبل حتى تبادل رمز اللقاء — يقلّل قلق الانتظار في مكان قد يكون غير مألوف.
- **قناة دعم مباشرة**: زر ثابت في صفحة الحساب يفتح محادثة واتساب مباشرة (يحتاج ضبط `VITE_SUPPORT_WHATSAPP` برقم دعم حقيقي قبل الإطلاق — القيمة الحالية عنصر نائب).
- **شريط الرحلة القادمة يعمل بلا إنترنت أيضاً**: يعتمد الآن على نفس التخزين المحلي المستخدم لرمز اللقاء عند انقطاع الاتصال، بدل الاختفاء بصمت.
- **وضع داكن يدوي**: الألوان كانت جاهزة في الكود منذ بداية العمل على الهوية البصرية، أُضيف فقط مفتاح تفعيل من صفحة الحساب (`lib/theme.ts`) محفوظ محلياً.

## ثلاث إضافات أمان وثقة أخيرة

- **آلية إبلاغ حقيقية** (مختلفة عن التقييم بالنجوم): جدول `reports` جديد بالكامل، زر "الإبلاغ عن مشكلة" في كل رحلة مكتملة، وتبويب "البلاغات" في لوحة الإدارة مع إجراء حظر مباشر للمُبلَّغ عنه إن لزم.
- **قناة SMS احتياطية** (`lib/sms.ts`) عبر Twilio REST — تُستخدم فقط للإشعارات الحرجة (قبول حجز، وصول السائق، نتيجة التوثيق) وفقط عندما لا يكون تيليجرام مرتبطاً، لضبط التكلفة. تبقى معطَّلة بصمت حتى تُضبط `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_FROM_NUMBER` — لا تكسر شيئاً بدونها.
- **مشاركة كود الإحالة عبر واتساب مباشرة** بدل الاعتماد فقط على قائمة مشاركة النظام العامة.

## نظام "أدمن مساعد" بصلاحيات جزئية

- **جدول الصلاحيات**: عمود `adminPermissions` جديد على المستخدمين (مصفوفة من قائمة مغلقة ومُتحقَّق منها في الباك-إند، وليست نصاً حراً): `users`، `verifications`، `reports`، `trips_bookings`، `pricing`، `catalog`.
- **الأمان مبني على مبدأ صارم**: `isAdmin=true` (أدمن كامل) يملك كل شيء دائماً بغض النظر عن هذه القائمة. فقط أدمن كامل يستطيع منح أو سحب صلاحية لأي مستخدم — مسار `POST /admin/users/:id/permissions` محمي حصراً بـ `requireAdmin` غير القابل للتفويض، حتى لا يستطيع أدمن مساعد منح نفسه أو غيره صلاحيات أعلى مهما كانت صلاحياته.
- **إجراءات حساسة تبقى لأدمن كامل فقط** بغض النظر عن الصلاحيات الممنوحة: حظر/رفع حظر مستخدم، حذف حساب، منح "ثقة الرحلات الحساسة"، مكافآت النقاط اليدوية.
- **الواجهة تتكيّف تلقائياً**: لوحة الإدارة تعرض فقط التبويبات التي يملك المستخدم صلاحية الوصول إليها؛ تبويب "المشرفون" (لمنح/سحب الصلاحيات) يظهر فقط لأدمن كامل.

## ما كان منسياً فعلاً (بعد مراجعة أعمق قبل الإطلاق)

- **سياسة الخصوصية وشروط الاستخدام**: صفحتان حقيقيتان الآن (`/privacy`, `/terms`)، متاحتان بلا تسجيل دخول، ومرتبطتان من تذييل صفحة الهبوط ومن خطوة إكمال الملف الشخصي. **هذه ضرورية فعلياً قبل نشر مشروع Google OAuth للعامة** — Google تطلب رابط سياسة خصوصية حقيقياً، وبدونه يبقى التطبيق في وضع "Testing" المحدود بـ100 مستخدم.
- **إقرار بلوغ 18 عاماً**: مربع اختيار إلزامي عند إكمال الملف الشخصي، مرتبط بحقل `ageConfirmedAt` جديد في قاعدة البيانات — لا يمكن المتابعة بدونه.
- **حذف الحساب الذاتي**: زر "حذف حسابي نهائياً" في صفحة الحساب — يُجهِّل البيانات الشخصية (الاسم، الصورة، البريد، الهاتف) بدل حذف صفّي فعلي، حفاظاً على سلامة سجل التقييمات التاريخي للأطراف الأخرى.
- **تنبيه لمستخدمي آيفون**: ملاحظة واضحة في قسم تيليجرام تشرح أن إشعارات الويب لا تصل على iOS بدون ربط تيليجرام — قيد حقيقي في المنصة لا حل برمجي له ضمن استراتيجية الإطلاق الحالية (رابط ويب بلا تثبيت).
- **نسخ احتياطي لقاعدة البيانات**: لم يُبنَ أي كود لهذا — Supabase توفّر نسخاً احتياطية يومية تلقائية على خطة Pro فما فوق (وPoint-in-Time Recovery على خطط أعلى). تحقق من إعدادات النسخ الاحتياطي في لوحة Supabase قبل الإطلاق الفعلي، فهذا إعداد في لوحتهم لا في هذا الكود.

## قرار سياسة صريح: لا سفر لقاصر بمفرده — تعديل عن المواصفة الأصلية

المواصفة الأصلية (`golog-spec.md`) كانت تسمح بحجز نيابة عن قاصر يسافر بمفرده، بآلية OTP على مرحلتين (استلام من نقطة الانطلاق، ثم تسليم منفصل عند الوجهة لطرف مستلم) — على غرار تسليم الطرود بالضبط. هذه الآلية كانت مطبَّقة فعلياً في نسخة سابقة من الكود.

**تم اتخاذ قرار منتج صريح بإلغاء هذا المسار بالكامل**: لا يُسمح بأي حال بسفر قاصر عبر التطبيق دون رفقة فعلية من أحد أبويه أو وصيّه الشرعي على متن الرحلة نفسها. لا يوجد أي مسار برمجي لإرسال قاصر بمفرده — لا حجز مستقل باسمه، ولا رمزي استلام/تسليم منفصلين، ولا بيانات "ولي أمر/طرف مستلم".

**التطبيق العملي**: أي قاصر يرافق راكباً بالغاً يُحتسب ضمن حجز ذلك الراكب نفسه (عدد المقاعد `seatsBooked` يغطي حجم المجموعة)، مع حقل معلوماتي بسيط `accompaniedMinorsCount` يُظهر للسائق عدد الأطفال المرافقين دون أن يُنشئ أي آلية تأكيد منفصلة — فالوصي الحاضر فعلياً هو من يستخدم رمز اللقاء الوحيد نفسه. رحلات "نسائي وعائلي" باتت مقيَّدة بالراكبات الإناث فقط (لا استثناء لحجز قاصر منفرد).

## استراتيجية الإطلاق (محدَّثة)

الإصدار الأول = **رابط ويب عادي فقط**. لا يوجد أي منطق تثبيت أو "أضف للشاشة
الرئيسية" في الكود — تحقق من ذلك: لا يوجد `manifest.json` ولا Service
Worker ولا أي مكوّن يطلب التثبيت. يُشارك الرابط مباشرة داخل مجموعات
واتساب. تغليف Capacitor لأندرويد مؤجَّل لمرحلة لاحقة (نفس كود React، جهد
إضافي بسيط عند الحاجة).

## ما تبقّى قبل الإطلاق الفعلي

- **حساب Supabase حقيقي**: إنشاء المشروع، `drizzle-kit push` على القاعدة الفعلية، تفعيل Storage، ثم تعبئة جدول `cities`/`crossings` بالمدن والمعابر الحقيقية عبر لوحة الإدارة (تم التحقق محلياً أن هذه الخطوة تعمل بلا أخطاء، تبقى فقط بحساب حقيقي).
- **مفاتيح حقيقية**: Google OAuth (مشروع بوضع Production لا Testing عند تجاوز 100 مستخدم)، بوت Telegram حقيقي، مفاتيح Supabase Storage S3.
- **جولة اختبار كاملة بمتصفح حقيقي على جهاز المستخدم**: التحقق المحلي في هذه الجلسة أثبت أن السيرفر وقاعدة البيانات والواجهة تعمل معاً فعلياً (وليس فقط فحص أنواع) — لكن لم تُختبر بعد دورة كاملة بمتصفح حقيقي وحساب Google حقيقي (تسجيل دخول → نشر رحلة → حجز → OTP → تقييم). موثّق خطوة بخطوة في دليل التشغيل المحلي المنفصل.
- **اختبارات آلية**: لا يوجد اختبارات وحدة بعد.
- **جاهزية تشغيلية بشرية** (لا تحتاج كوداً، لكنها ضرورية قبل مشاركة الرابط): من سيراجع تبويب البلاغات وخلال كم ساعة؟ استشارة قانونية قصيرة حول وضعك كصاحب منصة؟ تجنيد 3-5 سائقين موثوقين قبل دعوة أي راكب لتفادي شاشات فارغة؟
- بعض التبسيطات المقصودة مقارنة بالنسخة الأصلية القديمة: صفحة الأرباح لا
  تعرض رسوماً بيانية شهرية (فقط إجماليات)، ولوحة الإدارة مبسّطة (بدون رسوم
  بيانية تفاعلية)؛ يمكن توسيعها لاحقاً إذا لزم.

## إعداد التشغيل والنشر — Supabase + Vercel فقط

**الجواب المباشر: لا تحتاج أي منصة أخرى.** لا حاجة لـ Railway أو Render أو
حتى شراء دومين. Vercel يعطي رابطين مجانيين من نوع `xxx.vercel.app` —
كافيان تماماً لمشاركة رابط في مجموعات واتساب. دومين مخصص لاحقاً هو تحسين
اختياري بحت، وليس شرطاً لأي خطوة هنا.

**قرار معماري مهم يترتب على هذا**: Vercel لا يُشغّل عملية Node.js دائمة
مثل Railway — بل يُشغّل الكود كدوال منفصلة (Serverless Functions) عند كل
طلب. لهذا الباك-إند والواجهة الآن **مشروعا Vercel منفصلان** (بدومينين
مختلفين تحت نفس حسابك)، وليسا مُقدَّمين من عملية واحدة كما في الخطة
السابقة. هذا يعني الحاجة لضبط CORS وكوكي عابر للنطاقات — كلاهما مُهيَّأ
مسبقاً في الكود، فقط اتبع متغيرات البيئة أدناه بدقة.

### 1. مشروع Supabase (قاعدة البيانات + التخزين)

1. أنشئ مشروعاً في supabase.com.
2. **رابط قاعدة البيانات — نقطة حرجة لـ Vercel تحديداً**: من
   Project Settings → Database، لا تستخدم رابط "Direct connection"
   العادي (منفذ 5432). استخدم بدلاً منه رابط **Transaction pooler**
   (منفذ 6543، يظهر في نفس الصفحة). السبب: كل دالة Vercel قد تفتح اتصال
   جديد بقاعدة البيانات، ودوال كثيرة متزامنة مع اتصال مباشر تستنفد حد
   اتصالات Postgres خلال دقائق. الـ pooler مصمم تحديداً لهذا النمط
   اللاخادومي.
3. أنشئ Bucket من Storage باسم مثلاً `golog-uploads`.
4. من Project Settings → Storage → **S3 Connection**، اضغط
   "Create access key" واحفظ القيم الثلاث (Access Key ID، Secret Access
   Key، Region).
5. شغّل الترحيل والتعبئة الأولية (من جهازك، مرة واحدة):
   ```bash
   cd packages/db
   DATABASE_URL="<رابط الـ pooler>" npm run push
   DATABASE_URL="<رابط الـ pooler>" npm run seed
   ```

### 2. مشروع Google OAuth

كما سبق شرحه: Google Cloud Console → OAuth consent screen → Credentials
→ Create OAuth client ID (Web application). لن تعرف الـ redirect URI
النهائي إلا بعد الخطوة 4 (نشر الباك-إند على Vercel وحصولك على رابطه) —
عد لهذه الخطوة لإضافته لاحقاً، هذا طبيعي.

### 3. بوت تيليجرام

كما سبق: `/newbot` عبر BotFather، احفظ الـ token. خطوة `/setdomain` تحتاج
أيضاً رابط الواجهة النهائي من Vercel — نُكملها في الخطوة 6.

### 4. نشر الباك-إند على Vercel

1. من لوحة Vercel: **Add New → Project**، اربط مستودع GitHub.
2. **Root Directory**: اضبطه على `packages/api-server` (Vercel يكتشف
   الـ monorepo تلقائياً ويُثبّت كل الحزم المرتبطة عبر workspaces رغم ذلك).
3. **Framework Preset**: اختر "Other".
4. **Build Command**: اتركه فارغاً (لا حاجة لبناء — الدوال تُنفَّذ من
   TypeScript مباشرة).
5. أضف متغيرات البيئة التالية في إعدادات المشروع (Settings → Environment Variables):

   ```bash
   DATABASE_URL=<رابط الـ pooler من Supabase، منفذ 6543>
   SESSION_SECRET=<قيمة عشوائية طويلة>
   PUBLIC_URL=https://golog-api.vercel.app        # سيُستبدل برابطك الفعلي بعد أول نشر
   WEB_ORIGIN=https://golog-web.vercel.app         # رابط مشروع الواجهة (الخطوة 6)
   COOKIE_SAME_SITE=none                           # إلزامي لأن الواجهة والباك-إند نطاقان مختلفان على Vercel

   GOOGLE_CLIENT_ID=...
   GOOGLE_CLIENT_SECRET=...

   TELEGRAM_BOT_TOKEN=...
   TELEGRAM_BOT_USERNAME=GologApp_bot

   ADMIN_EMAILS=you@gmail.com

   # اختياري — قناة SMS احتياطية للإشعارات الحرجة فقط عند عدم ربط تيليجرام
   TWILIO_ACCOUNT_SID=...
   TWILIO_AUTH_TOKEN=...
   TWILIO_FROM_NUMBER=+1...

   SUPABASE_PROJECT_REF=abcdefghijklmnop
   SUPABASE_S3_ACCESS_KEY_ID=...
   SUPABASE_S3_SECRET_ACCESS_KEY=...
   SUPABASE_S3_REGION=us-east-1
   SUPABASE_STORAGE_BUCKET=golog-uploads
   ```

6. اضغط Deploy. بعد اكتمال النشر، انسخ الرابط الفعلي الذي يعطيك إياه
   Vercel (مثال: `golog-api-xyz123.vercel.app`)، وحدّث به قيمتَي
   `PUBLIC_URL` في هذا المشروع نفسه، ثم أعد النشر (Redeploy) ليأخذ القيمة
   الصحيحة.

### 5. نشر الواجهة على Vercel

1. **Add New → Project** مرة أخرى (نفس المستودع).
2. **Root Directory**: `packages/web`.
3. **Framework Preset**: Vercel يكتشف Vite تلقائياً — اتركه كما هو.
4. أضف متغيرات البيئة:
   ```bash
   VITE_API_BASE_URL=https://<رابط مشروع الباك-إند من الخطوة 4>/api
   VITE_TELEGRAM_BOT_USERNAME=GologApp_bot
   VITE_SUPPORT_WHATSAPP=905XXXXXXXXX   # رقم دعم حقيقي بصيغة دولية بدون + أو مسافات
   ```
5. Deploy. انسخ رابط هذا المشروع أيضاً (مثال: `golog-web-xyz123.vercel.app`).

### 6. الربط النهائي بين المشاريع الثلاثة

بعد أن أصبح لديك رابطا Vercel الفعليان:

1. ارجع لمشروع **الباك-إند** على Vercel → حدّث `WEB_ORIGIN` برابط
   الواجهة الفعلي → Redeploy.
2. **Google Cloud Console** → أضف
   `https://<رابط الباك-إند>/api/auth/google/callback` إلى Authorized
   redirect URIs.
3. **BotFather** → `/setdomain` → اختر بوتك → أدخل رابط **الواجهة**
   (بدون `https://`، فقط الدومين، مثال: `golog-web-xyz123.vercel.app`).
4. **سجّل ويبهوك تيليجرام يدوياً** (لا يُسجَّل تلقائياً على Vercel، انظر
   الملاحظة أدناه):
   ```bash
   cd packages/api-server
   PUBLIC_URL="https://<رابط الباك-إند>" TELEGRAM_BOT_TOKEN="..." npm run register-telegram-webhook
   ```

> **ملاحظة فنية**: على استضافة بعملية دائمة (كـ Railway) كان يمكن تسجيل
> الويبهوك تلقائياً عند إقلاع السيرفر. على Vercel اللاخادومي هذا غير
> مناسب (كل طلب قد يُشغّل نسخة جديدة من الكود)، فحوّلته إلى سكربت يدوي
> يُشغَّل مرة واحدة فقط بعد كل نشر يتغيّر فيه رابط الباك-إند.

### 7. التطوير محلياً (قبل أو بعد النشر، لا فرق)

```bash
# الباك-إند (طرفية أولى) — يحتاج .env في packages/api-server بنفس متغيرات الخطوة 4
# محلياً: WEB_ORIGIN=http://localhost:5173, COOKIE_SAME_SITE=lax (لا حاجة none محلياً)
cd packages/api-server && npm install && npm run dev

# الواجهة (طرفية ثانية) — لا حاجة لـ VITE_API_BASE_URL محلياً، الافتراضي "/api" يعمل عبر بروكسي vite
cd packages/web && npm install && npm run dev
```

### 8. قائمة الفحص قبل مشاركة الرابط في أي مجموعة واتساب

هذه خطوة تحقّق بشرية، نفّذها بنفسك بحساب حقيقي على رابط الواجهة الفعلي:

- [ ] تسجيل الدخول عبر Google يعمل ويُنشئ الحساب بنجاح
- [ ] تسجيل الدخول عبر Telegram Login Widget يعمل (يحتاج `/setdomain` من الخطوة 6.3)
- [ ] إكمال الملف الشخصي (اختيار الجنس) يعمل
- [ ] التبديل بين وضع سائق/راكب يعمل
- [ ] نشر رحلة (كسائق) يظهر في نتائج بحث حساب آخر (كراكب)
- [ ] حجز مقعد → قبول السائق → ظهور رمز اللقاء → تأكيد السائق للرمز → اكتمال الحجز
- [ ] التقييم بعد اكتمال الرحلة يعمل
- [ ] رفع وثيقة توثيق سائق (Supabase Storage) يعمل ويظهر في لوحة الإدارة
- [ ] حسابك مُرقّى لأدمن فعلياً (تحقق من `ADMIN_EMAILS`) وتظهر لك لوحة الإدارة
- [ ] رحلة "نسائي وعائلي" تُرفض لسائق ذكر غير موثوق، وتُقبل لحساب أنثى
- [ ] طلب شحن طرد ينشر ويظهر بشكل صحيح
- [ ] إشعار تيليجرام يصل فعلياً بعد ربط الحساب (تحقق من الخطوة 6.4)
- [ ] كوكي الجلسة يبقى بعد تحديث الصفحة (يتحقق من صحة `COOKIE_SAME_SITE=none` بين النطاقين)
- [ ] الإبلاغ عن مشكلة في رحلة مكتملة يصل فعلياً لتبويب "البلاغات" في لوحة الإدارة
- [ ] منح صلاحية مساعدة لمستخدم من تبويب "المشرفون" يعمل، وتظهر له فقط التبويبات المسموحة عند دخوله
- [ ] صفحتا /privacy و/terms تفتحان بلا تسجيل دخول
- [ ] لا يمكن إكمال الملف الشخصي بدون تفعيل مربع تأكيد العمر
- [ ] حذف الحساب من صفحة الحساب يعمل، ولا يمكن تسجيل الدخول بنفس الحساب بعده

فقط بعد اجتياز هذه القائمة كاملة، شارك الرابط في أول مجموعة واتساب صغيرة
موثوقة — وليس على نطاق واسع مباشرة.
